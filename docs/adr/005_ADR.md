# 005_ADR: Normes de Commit, Workflow de Validation et Sécurité des Opérations Git

- **Statut :** Accepté (Accepted)

## 1. Contexte & Problématique

La rédaction des messages de commit et l'exécution d'opérations Git par un agent IA nécessitent un contrôle utilisateur absolu, modifiable et sans risque d'action unilatérale ou de validation précipitée.

Taper ou corriger de longs messages de commit directement dans la ligne de commande du terminal est rigide et peu pratique. Passer par un fichier de brouillon intermédiaire, effectuer une alerte `git status` préalable et exiger l'accord explicite de l'utilisateur avant toute commande Git sécurise la gouvernance du projet.

---

## 2. Décisions d'Architecture

### D1. Norme Conventional Commits en Français
- **Structure :** Tout message de commit respecte la norme **Conventional Commits** (`feat:`, `fix:`, `docs:`, `chore:`, etc.) et est rédigé en **français**.
- **Paragraphe de Synthèse :** Le corps du message inclut impérativement un paragraphe explicatif de synthèse contextualisant l'ensemble des changements apportés.
- **Précision Grammaticale :** Accord strict `'fichier modifié:'` (un seul fichier) / `'fichiers modifiés:'` (plusieurs fichiers).
- **Marge des Listes :** Tirets collés à la marge gauche sans espace.

### D1.1. Formatage des Noms de Fichiers dans les Listes
- **Règle Stricte de Syntaxe :** Tous les noms de fichiers énumérés dans le message de commit sont impérativement entourés de simple quote et d'un backtick sous la forme exacte **`'`.nom_du_fichier`'`**.

### D1.2. Modèle et Exemple Complet d'un Message Conforme
```text
feat(scope): résumé concis du changement

Paragraphe de synthèse globale expliquant le contexte, la motivation et l'impact des modifications apportées au projet.

fichiers modifiés:
- '`.gitignore`': description de la modification
- '`package.json`': description de la modification
```

### D2. Workflow de Validation par Fichier Intermédiaire (`./tmp/git/git-commit-message.md`) & Alerte Pre-Commit
1. **Proposition :** L'agent rédige et soumet sa proposition de message de commit à l'utilisateur.
2. **Fichier Brouillon :** Après premier accord, l'agent écrit le message dans le fichier temporaire `./tmp/git/git-commit-message.md`. L'utilisateur peut ainsi le réviser ou le modifier confortablement dans son éditeur.
3. **Vérification Pre-Commit (`git status`) :** L'agent exécute impérativement `git status` et alerte l'utilisateur si des fichiers modifiés ou non suivis ne sont pas indexés (non staged).
4. **Commit Effectif :** Sur confirmation finale de l'utilisateur, l'agent exécute l'indexation (`git add .`) puis le commit via la commande `git commit -F ./tmp/git/git-commit-message.md`.

### D3. Exclusion de Sécurité (`temp/` & `tmp/`)
- Les répertoires `temp/` et `tmp/` servant aux fichiers de travail temporaires, ils sont exclus dans `.gitignore` et ne sont jamais indexés dans le dépôt Git.

### D4. Interdiction Stricte d'Opérations Git Sans Accord Explicite Préalable
- **Souveraineté de l'Utilisateur :** L'agent IA ne doit **JAMAIS** prendre l'initiative d'exécuter une commande Git (`git add`, `git commit`, `git checkout`, `git push`, etc.) de son propre chef sans demande explicite.
- **Procédure d'Explication & Autorisation Obligatoire :** Pour toute opération Git, l'agent doit impérativement :
  1. Expliquer clairement à l'utilisateur l'opération Git envisagée et la liste exacte des fichiers concernés.
  2. Solliciter l'accord préalable et explicite de l'utilisateur.
  3. Attendre la validation sans réserve de l'utilisateur avant de lancer la moindre commande Shell Git.

## 3. Conséquences

### Positives :
- Confort total pour l'utilisateur qui peut relire et corriger le message dans son IDE avant commit.
- Sécurité Git maximale : zéro action unilatérale de l'agent et contrôle utilisateur total sur l'historique du projet.
