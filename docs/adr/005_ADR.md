# 005_ADR: Normes de Commit, Workflow de Validation, Formatage et Sécurité Git

- **Statut :** Accepté (Accepted)
- **Auteurs :** Thomas Gauthier & Antigravity (Google DeepMind Team)

## 1. Contexte & Problématique

La rédaction des messages de commit, la gestion des numéros de version et l'exécution d'opérations Git par un agent IA nécessitent un contrôle utilisateur absolu, modifiable et sans risque d'action unilatérale ou de validation précipitée.

Taper ou corriger de longs messages de commit directement dans le terminal est rigide. Passer par un fichier de brouillon intermédiaire, effectuer une alerte `git status` préalable, respecter le formatage par backticks, guider le développeur sur l'opportunité d'un bump de version et exiger l'accord explicite de l'utilisateur sécurise la gouvernance du projet.

---

## 2. Décisions d'Architecture

### D1. Norme Conventional Commits en Français
- **Structure :** Tout message de commit respecte la norme **Conventional Commits** (`feat:`, `fix:`, `docs:`, `chore:`, etc.) et est rédigé en **français**.
- **Paragraphe de Synthèse :** Le corps du message inclut impérativement un paragraphe explicatif de synthèse contextualisant l'ensemble des changements apportés.
- **Précision Grammaticale :** Accord strict `'fichier modifié:'` (un seul fichier) / `'fichiers modifiés:'` (plusieurs fichiers).
- **Marge des Listes :** Tirets collés à la marge gauche sans espace.

### D1.1. Formatage des Noms de Fichiers et Symboles de Code par Backticks
- **Règle Stricte de Noms de Fichiers :** Tous les noms de fichiers énumérés dans la liste du message de commit sont impérativement encadrés par des backticks uniquement (ex: `.gitignore`, `package.json`), sans aucun guillemet simple ou double.
- **Règle Stricte de Symboles et Extraits de Code :** Dans le corps et les descriptions des commits, tous les noms de fonctions, variables, options et termes techniques sont également encadrés par des backticks (ex: `os.tmpdir()`, `path.join()`, `node:test`, `contents: read`).

### D1.2. Modèle et Exemple Complet d'un Message Conforme
```text
feat(scope): résumé concis du changement

Paragraphe de synthèse globale expliquant le contexte, la motivation et l'impact des modifications apportées au projet, avec encadrement des fonctions comme `os.tmpdir()`.

fichiers modifiés:
- `.gitignore`: description de la modification avec `node_modules/`
- `package.json`: description de la modification avec `engines`
```

### D1.3. Évaluation Pré-Commit du Bump de Version (Conseil & Guidage SemVer)
- **Analyse Obligatoire :** Avant toute proposition de commit, l'agent IA évalue l'impact du code modifié selon la grille SemVer (Conservation, PATCH, MINOR, MAJOR).
- **Conseil Proactif :** L'agent soumet au développeur une recommandation explicite et argumentée sur l'opportunité ou non de faire évoluer le numéro de version (dans `package.json`, `herdr-plugin.toml` et `CHANGELOG.md`).

### D2. Workflow de Validation par Fichier Intermédiaire (`./tmp/git/git-commit-message.md`) & Alerte Pre-Commit
1. **Évaluation SemVer :** L'agent évalue le bump de version et soumet sa recommandation.
2. **Proposition :** L'agent rédige et soumet sa proposition de message de commit à l'utilisateur.
3. **Fichier Brouillon :** Après premier accord, l'agent écrit le message dans le fichier temporaire `./tmp/git/git-commit-message.md`. L'utilisateur peut ainsi le réviser ou le modifier confortablement dans son éditeur.
4. **Vérification Pre-Commit (`git status`) :** L'agent exécute impérativement `git status` et alerte l'utilisateur si des fichiers modifiés ou non suivis ne sont pas indexés (non staged).
5. **Commit Effectif :** Sur confirmation finale de l'utilisateur, l'agent exécute l'indexation (`git add .`) puis le commit via la commande `git commit -F ./tmp/git/git-commit-message.md`.

### D2.4. Automatisation des Tests Pre-Commit (`npm run precommit` & Hook Natif `.git/hooks/pre-commit`)
- **Script NPM Dédié :** Un script `"precommit": "npm test"` est déclaré dans `package.json` pour permettre l'exécution manuelle ou automatisée de la suite de tests avant validation.
- **Hook Git Natif Inviolable :** Un hook natif Shell `.git/hooks/pre-commit` (exécutable via `chmod +x`) est activé dans le dépôt local.
- **Interruption Automatique en Cas d'Échec :** Lors de chaque exécution de `git commit`, le hook natif lance automatiquement `npm test`. En cas d'échec de test ou de désynchronisation de version sémantique (SemVer), Git interrompt immédiatement le commit avec le code d'erreur `1`, garantissant qu'aucun code régressif ne soit validé.

### D3. Exclusion de Sécurité (`temp/` & `tmp/`)
- Les répertoires `temp/` et `tmp/` servant aux fichiers de travail temporaires, ils sont exclus dans `.gitignore` et ne sont jamais indexés dans le dépôt Git.

### D4. Interdiction Stricte d'Opérations Git Sans Accord Explicite Préalable
- **Souveraineté de l'Utilisateur :** L'agent IA ne doit **JAMAIS** prendre l'initiative d'exécuter une commande Git (`git add`, `git commit`, `git checkout`, `git push`, etc.) de son propre chef sans demande explicite.
- **Procédure d'Explication & Autorisation Obligatoire :** Pour toute opération Git, l'agent doit impérativement :
  1. Expliquer clairement à l'utilisateur l'opération Git envisagée et la liste exacte des fichiers concernés.
  2. Solliciter l'accord préalable et explicite de l'utilisateur.
  3. Attendre la validation sans réserve de l'utilisateur avant de lancer la moindre commande Shell Git.

## 3. Conséquences

### Positives :
- Lisibilité optimale du journal de commits sur GitHub.
- Guidage proactif et intelligent de la dynamique de version par l'IA.
- Protection absolue contre les commits régressifs ou désynchronisés grâce au hook pre-commit.
