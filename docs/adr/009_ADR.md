# 009_ADR: Pipeline d'Intégration Continue (GitHub Actions CI)

- **Statut :** Accepté (Accepted)

## 1. Contexte & Problématique

Pour garantir que tout commit pushé sur la branche de production `master` distante ou soumis via une Pull Request respecte les critères de qualité, d'exécution de tests et de compilation du bundle, il est nécessaire d'automatiser les vérifications au sein d'un pipeline d'intégration continue.

Les branches de travail (`dev`, `feature/*`) demeurent exclusivement locales sur le poste développeur, seule la branche `master` étant publiée sur le dépôt GitHub distant.

---

## 2. Décisions d'Architecture

### D1. Choix du Runner & Emplacement
- **Emplacement :** Le fichier de workflow est déclaré sous le répertoire standard `.github/workflows/ci.yml`.
- **Plateforme :** Utilisation des GitHub Actions avec des runners Linux `ubuntu-latest`.
- **Déclencheurs (Triggers) :** Push et Pull Request ciblant exclusivement la branche `master`.

### D2. Matrice Multi-Versions Node.js & Sécurité 2026
- **Matrice Node.js :** Exécution automatisée sur les versions Active LTS de Node.js (`20.x`, `22.x`).
- **Spécification Engines dans `package.json` :** Déclaration de `"engines": { "node": ">=18.11.0" }`.
- **Permissions Restreintes :** Déclaration de `permissions: contents: read` au sommet du workflow.
- **Gestion des Concurrences :** Utilisation du bloc `concurrency` avec `cancel-in-progress: true` pour annuler les builds obsolètes.

### D3. Étapes du Pipeline (Install ➔ Test ➔ Build)
1. `npm ci` (Installation propre avec cache `npm`).
2. `npm test` (Exécution Headless des tests unitaires `node:test`).
3. `npm run build` (Validation de la compilation `esbuild`).

---

## 3. Conséquences

### Positives :
- Dépôt GitHub distant ultra-épuré (seule la branche `master` y réside).
- Détection immédiate des régressions lors de chaque publication sur `master`.
- Validation de la compatibilité Headless du serveur mock en environnement Linux.
