# 015_ADR: Mesure de Couverture de Code par c8 et Rapports d'Analyse Istanbul

- **Statut :** Accepté (Accepted)
- **Auteurs :** Thomas Gauthier & Antigravity (Google DeepMind Team)
- **Date :** 2026-07-29
- **Version du Plugin :** v1.0.0-alpha.1

---

## 1. Contexte & Problématique

Pour maintenir une qualité d'ingénierie de classe mondiale et s'assurer que l'ensemble des modules Pure JavaScript (`src/`) et des scripts utilitaires (`bin/`) sont rigoureusement validés par des tests unitaires déterministes (ADR-007), le projet `herdr-voice` a besoin d'un outil de mesure de la couverture de code (*Code Coverage*).

La solution retenue doit s'intégrer harmonieusement avec le runner de test natif de Node.js (`node --test`), sans imposer de transpilation lourde ou de modification du code source, tout en offrant une visualisation graphique interactive pour le développeur et l'architecte.

---

## 2. Décisions d'Architecture

### D1. Adoption de `c8` comme Moteur de Couverture V8 Natif
- Le projet adopte **`c8`** en dépendance de développement (`devDependencies`).
- `c8` utilise les fonctionnalités d'analyse de couverture intégrées au moteur JavaScript V8 de Node.js, garantissant une mesure ultra-rapide, exacte et sans transpilation préalable.

### D2. Double Restitution des Rapports (Console & Site Web HTML Interactif)
- La mesure de couverture génère simultanément deux types de rapports :
  1. **Synthèse Console (`text`) :** Un tableau synthétique imprimé dans le terminal lors de l'exécution du test.
  2. **Rapport Web Interactif Istanbul (`html`) :** Un site web autonome généré dans le répertoire **`./coverage/index.html`**.
- L'interface HTML offre une visualisation graphique couleur par fichier (vert pour le code couvert, rouge pour le code non exécuté, jaune pour les branches partielles) et un surlignage ligne par ligne.

### D3. Commande NPM & Configuration de la Conservation Git
- La commande **`npm run coverage`** est ajoutée au fichier `package.json` :
  ```json
  "scripts": {
    "coverage": "c8 --reporter=text --reporter=html npm test"
  }
  ```
- Le répertoire de sortie `./coverage/` est strictement exclu du suivi Git via `.gitignore` et ignoré par le linter StandardJS (`standard.ignore` dans `package.json`).

### D4. Organisation Centralisée des Fixtures Statiques (`test/fixtures/`)
- Afin de maximiser la lisibilité pour le développeur et d'éviter les chaînes dynamiques en dur dans les fichiers de test, l'ensemble des jeux de données d'entrée (configurations TOML valides, syntaxes corrompues et schémas invalides) sont centralisés et versionnés dans le répertoire dédié **`test/fixtures/`**.

### D5. Intégration dans le Workflow de Release Officiel
- Pour éviter le bruit dans l'historique Git à chaque commit intermédiaire, le badge de couverture du `README.md` est mis à jour lors de la procédure officielle de publication (version bump / release candidate).
- Le Workflow de Release impose de :
  1. Exécuter `npm run coverage` pour certifier le taux de couverture global.
  2. Mettre à jour la version (`package.json`, `herdr-plugin.toml`, `CHANGELOG.md`) et la valeur du badge dans `README.md`.
  3. Valider l'inviolabilité de la suite de tests via `npm run precommit`.

## 3. Conséquences

### Positives :
- Visualisation chirurgicale des zones de code non couvertes par les tests.
- Zéro dégradation des performances lors de l'exécution standard des tests (`npm test`).
- Outil léger et parfaitement aligné avec la philosophie de test natif `node:test` (ADR-007).
