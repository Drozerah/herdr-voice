# 016_ADR: Centralisation de la Sécurité Logicielle et Masquage Automatique des Données Sensibles

- **Statut :** Accepté (Accepted)
- **Auteurs :** Thomas Gauthier & Antigravity (Google DeepMind Team)
- **Date :** 2026-07-30
- **Version du Plugin :** v1.0.0-alpha.1

---

## 1. Contexte & Problématique

Dans le cadre d'un plugin d'intégration de services d'inférence vocale (TTS) interagissant avec des API Cloud tierces (OpenAI, ElevenLabs, Azure Speech, etc.), des données d'authentification sensibles (clés d'API, jetons de session `Bearer`) circulent dans la configuration et les flux du plugin.

Afin de prévenir toute fuite de secrets (*Credential Leakage*) dans les fichiers de logs système ou les notifications visuelles Herdr Toast UI, le projet `herdr-voice` doit garantir qu'aucune clé sensible ne puisse être imprimée en clair.

Conformément au principe de **Séparation des Responsabilités (*Separation of Concerns - SoC*)**, les fonctionnalités de sécurité ne doivent pas être dispersées dans les modules de journalisation ou de configuration, mais isolées dans un composant d'architecture dédié.

---

## 2. Décisions d'Architecture

### D1. Création du Module Dédié `src/security.js`
- L'ensemble des règles de sécurité, d'assainissement et de masquage de données sensibles est centralisé dans le module Pure JavaScript **`src/security.js`**.
- Ce module est la référence unique du projet pour toutes les opérations de contrôle de sécurité.

### D2. Masquage Automatique des Secrets (`sanitizeLogMessage`)
- Le module `src/security.js` expose la fonction `sanitizeLogMessage(message)` qui analyse et masque automatiquement les secrets avant tout traitement :
  - **Clés d'API TOML / JSON :** `api_key = "..."` ou `api_key: "..."` ➔ `api_key = "[REDACTED]"`.
  - **En-têtes d'Authentification HTTP :** `Authorization: Bearer secret-token` ➔ `Authorization: Bearer [REDACTED]`.
  - **Format de Clés Standard (OpenAI/ElevenLabs) :** `sk-proj-...` ou `sk-...` ➔ `[REDACTED]`.

### D3. Filtrage Systématique dans le Logger et le Toast UI
- Le service de journalisation **`src/logger.js`** invoque systématiquement `sanitizeLogMessage()` avant toute émission de message vers la console système ou vers l'API graphique `globalThis.herdr.ui.toast()`.

### D4. Co-location Obligatoire des Tests de Sécurité (`src/security.test.js`)
- Le module `src/security.js` possède son fichier de test unitaire natif co-localisé **`src/security.test.js`** pour valider avec un taux de couverture de 100 % le masquage des données sensibles.

---

## 3. Conséquences

### Positives :
- Garantie de sécurité de type *Zero-Leak Policy* contre les fuites de clés d'API.
- Architecture logicielle modulaire et respectueuse du principe de responsabilité unique (SRP/SoC).
- Auditabilité et testabilité simplifiées des règles de sécurité.

---

## 4. Conformité & Gouvernance

Toute nouvelle règle d'assainissement ou de masquage devra s'effectuer par enrichissement de `src/security.js` et révision *In Situ* du présent Acte d'Architecture conforme au format Google Cloud OKF v0.2.
